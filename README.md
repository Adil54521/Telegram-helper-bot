# Kuam Bot

Telegram-бот на Python 3.12 / aiogram 3 с CMS внутри Telegram, PostgreSQL, SQLAlchemy Async и Alembic.

## Возможности

- динамическое пользовательское меню и страницы из PostgreSQL;
- отдельные draft- и published-ревизии страниц;
- `/admin` с ролями `SUPER_ADMIN`, `ADMIN`, `EDITOR`;
- повторная проверка прав на каждом административном callback и FSM-шаге;
- редактирование текста/названия, предпросмотр и явная публикация;
- создание новых страниц из CMS с автоматически генерируемым уникальным key;
- произвольная вложенность страниц через PAGE-кнопки без ограничения глубины;
- безопасное удаление страниц с поиском входящих ссылок и защитой `main`;
- выбор пользовательского языка RU/KK с сохранением в PostgreSQL;
- локализованные ревизии страниц, кнопки и FAQ с предсказуемым RU fallback;
- документы и изображения страниц по Telegram `file_id`, локализованные подписи и draft/publish;
- CMS кнопок PAGE/URL/BACK: создание, редактирование, включение, порядок и подтверждаемое удаление;
- CMS FAQ и пользовательский FAQ из PostgreSQL;
- управление администраторами с защитой `SUPER_ADMIN_ID` и последнего активного SUPER_ADMIN;
- рассылки с фото по Telegram `file_id`, предпросмотром, throttling, обработкой блокировок и историей;
- опциональный grounded AI-ассистент по опубликованным страницам и активному FAQ;
- аудит изменений и публикаций;
- регистрация пользователей, просмотры страниц и базовая статистика;
- идемпотентное создание стартовых страниц и кнопок;
- Docker Compose: bot, PostgreSQL и локальный Adminer.

## Настройка Telegram

1. Откройте `@BotFather`, выполните `/newbot` и сохраните токен.
2. Узнайте свой числовой Telegram ID через `@userinfobot` или аналогичного бота.
3. Скопируйте `.env.example` в `.env` и заполните `BOT_TOKEN`, `POSTGRES_PASSWORD`, `SUPER_ADMIN_ID`.

Секреты из `.env` исключены из Git. `SUPER_ADMIN_ID` всегда распознаётся как супер-администратор, даже если таблица `admins` пуста; так можно восстановить доступ заменой значения и перезапуском контейнера.

## AI-ассистент

AI v1 использует официальный асинхронный Google Gen AI SDK и Gemini API. По умолчанию функция выключена и не влияет на остальные возможности бота.

```env
AI_ENABLED=true
AI_PROVIDER=gemini
GEMINI_API_KEY=
GEMINI_MODEL=
AI_SEMANTIC_SEARCH_ENABLED=false
AI_EMBEDDING_MODEL=gemini-embedding-2
AI_EMBEDDING_DIMENSION=768
GEMINI_INPUT_PRICE_PER_1M=0.30
GEMINI_OUTPUT_PRICE_PER_1M=2.50
AI_TIMEOUT_SECONDS=30
AI_COOLDOWN_SECONDS=8
```

После изменения конфигурации пересоберите и перезапустите bot:

```bash
docker-compose build bot
docker-compose up -d bot
```

При корректной конфигурации кнопка `🤖 Спросить ИИ` / `🤖 AI-дан сұрау` появляется только на главной странице. После входа AI остаётся в диалоговом режиме до нажатия `🏠 Завершить и в меню`: каждый вопрос обрабатывается как отдельный grounded RAG request без передачи истории переписки. Ассистент ищет до трёх релевантных фрагментов только в опубликованных ревизиях страниц и активном FAQ, ограничивает общий контекст и отвечает на выбранном пользователем языке. При retrieval=0 Gemini не вызывается. Черновики не используются. При отсутствии KK-перевода применяется RU fallback с соответствующей пометкой внутри AI-контекста.

AI v2 добавляет семантический индекс PostgreSQL/pgvector и Gemini Embeddings. Размерность индекса фиксирована на 768, RU и KK индексируются отдельно, а длинные страницы делятся на перекрывающиеся чанки. Индексация идемпотентна: SHA-256 позволяет не оплачивать embeddings для неизменённого содержимого. Синхронизация запускается вручную через `/admin → ИИ-ассистент → Индекс знаний` и требует подтверждения. До первой успешной синхронизации оставьте `AI_SEMANTIC_SEARCH_ENABLED=false`; после неё включение флага активирует hybrid semantic + lexical retrieval. При недоступности embeddings бот автоматически использует lexical fallback и не вызывает Gemini generation при отсутствии источников.

Обычный текст вне любого FSM возвращает пользователя на `main` и никогда не вызывает Gemini. Диагностика статуса, retrieval, соединения и persistent analytics доступна администраторам с правом просмотра статистики в разделе `/admin → ИИ-ассистент`. Analytics хранит только технические метрики, реальные token counts из Gemini metadata и рассчитанную по настроенным тарифам стоимость. Полные вопросы, ответы, prompt и knowledge context в БД не сохраняются. `HEALTH_CHECK` хранится отдельно и исключён из пользовательской статистики.

Стоимость является оценочной: Free Tier автоматически не определяется, а старые записи не пересчитываются после изменения тарифов — стоимость и применённые rates фиксируются в момент запроса.

Ограничения: документы и изображения не анализируются, нет истории диалога, web search, Redis или отдельного worker. Вопрос ограничен 1000 символами; действует простой in-memory cooldown.

Если кнопка AI не появляется, проверьте `AI_ENABLED`, непустые `GEMINI_API_KEY` и `GEMINI_MODEL`, затем изучите `docker-compose logs bot`. При ошибках API пользователь получает безопасное локализованное сообщение; ключ и полный запрос в логи не записываются.

## Импорт официальных Telegram-публикаций

Единая интеграция принимает новые публикации из настроенного Telegram channel, group или supergroup. Identity проверяется только по numeric chat ID; username, название группы и название forum topic не являются security identifiers. Поддерживаются `channel_post`, `edited_channel_post`, сообщения администраторов группы, anonymous admin posts от имени самой группы, albums и Forum Topics. Bot API не используется для чтения старой истории.

```env
CONTENT_CHAT_ID=-1001234567890
CONTENT_CHANNEL_NOTIFY_ADMINS=true
```

`CONTENT_CHANNEL_NOTIFY_ADMINS` сохраняется для обратной совместимости и задаёт начальное значение уведомлений, пока настройки импорта ещё не созданы в PostgreSQL. После первого открытия/изменения настроек в CMS источником истины становится переключатель `Уведомления` в `/admin → Telegram-публикации → Настройки импорта`. Его выключение подавляет обычные личные уведомления о новых публикациях, авточерновиках, автопубликациях и связанных материалах, но не останавливает импорт и автоматическую обработку.

Для каждой связи Topic → Page отдельно настраивается синхронизация редактирований: `OFF` (по умолчанию), `REVIEW` или `AUTO`. `AUTO` применяется только к подтверждённым Telegram-страницам с полным RU/KK содержимым и блокируется при наличии ручных CMS-изменений. REVIEW и конфликты сохраняются в PostgreSQL и открываются администратору для подтверждения.

Каждый успешный `PageService.publish()` ставит актуальную опубликованную revision в DB-backed очередь AI knowledge sync. Фоновый processor переживает рестарт, повторяет временные ошибки и не индексирует DRAFT. Пока embeddings ожидаются или недоступны, lexical retrieval читает текущую опубликованную revision непосредственно из CMS.

При пустом `CONTENT_CHAT_ID` интеграция выключена и не мешает запуску. Старый `CONTENT_CHANNEL_ID` временно поддерживается как deprecated fallback, но новые установки должны использовать `CONTENT_CHAT_ID`. Новые text/photo/document posts и части media groups сохраняются в PostgreSQL без скачивания файлов, Gemini и embeddings. `message_thread_id` сохраняется для forum topics, но темы пока не фильтруются. Модерация доступна в `/admin → Telegram-публикации`: администратор может вручную подготовить Page/FAQ, явно вызвать одно structured Gemini-преобразование или исключить публикацию. Page всегда создаётся как DRAFT и публикуется обычным CMS workflow.

Для group/supergroup бот проверяет отправителя через `getChatMember` и принимает только administrator/creator либо корректный anonymous admin post, где `sender_chat.id == chat.id`. Для этой проверки бот должен быть администратором группы; дополнительные права удаления сообщений, блокировки участников, публикации историй и т. п. не требуются.

По официальной документации Telegram bot-admin получает все сообщения группы. Если бот не назначен администратором, отключите Privacy Mode через `@BotFather → /setprivacy → Disable` и повторно добавьте бота в группу; иначе обычные сообщения могут не приходить. Настройка privacy mode программно невозможна.

## Первый запуск

```bash
docker compose up -d postgres
docker compose run --rm bot alembic upgrade head
docker compose up -d
docker compose logs -f bot
```

На системах с отдельным Compose выполните те же команды через `docker-compose`:

```bash
docker-compose up -d postgres
docker-compose run --rm bot alembic upgrade head
docker-compose up -d
```

После обновления проекта с версии `20260929_01` примените миграцию локализации:

```bash
docker-compose run --rm bot alembic upgrade head
# либо
docker compose run --rm bot alembic upgrade head
```

Миграция сохраняет исходные поля и переносит существующие страницы, кнопки и FAQ в русские translation-записи. Казахские переводы заполняются через CMS.

Бот использует long polling. Миграции не применяются автоматически и `create_all()` не используется.

После обновления примените новую AI analytics migration:

```bash
docker-compose run --rm bot alembic upgrade head
# либо
docker compose run --rm bot alembic upgrade head
```

Миграция `20260930_04` создаёт таблицу `ai_usage`; содержимое вопросов и ответов в неё не записывается. Миграция `20261005_05` включает расширение `vector` и создаёт `ai_knowledge_chunks`. Docker Compose использует PostgreSQL 16 с pgvector. Перед включением semantic retrieval выполните `alembic upgrade head`, затем ручную синхронизацию индекса в CMS.

## Adminer

Adminer доступен на `http://localhost:8080`:

- System: PostgreSQL
- Server: `postgres`
- Username/Password/Database: значения из `.env`

Порт привязан только к `127.0.0.1`. Не публикуйте Adminer в интернете; для production лучше вообще не запускать профиль технических инструментов или закрыть его VPN/аутентификацией.

## Работа

- `/start` — открыть опубликованную главную страницу.
- `/admin` — открыть разрешённые текущей роли разделы CMS.
- Страницы → выбрать страницу → изменить текст/название → подтвердить → предпросмотр → опубликовать.
- Страницы → Создать страницу → название → текст → предпросмотр → подтверждение. Системный key формируется автоматически; новая страница остаётся черновиком до явной публикации.
- Страница → Кнопки — управлять динамической inline-клавиатурой.
- Страница → Русский/Қазақша — редактировать переводы черновой ревизии.
- Страница → Вложения — добавлять документы и фотографии, подписи RU/KK, менять порядок и активность.
- FAQ — создавать и упорядочивать вопросы, включать и удалять их.
- FAQ CSV — скачать UTF-8 шаблон, импортировать только новые вопросы через preview и экспортировать текущий список без внутренних ID. Дубликаты определяются по нормализованному русскому вопросу; импорт никогда не обновляет и не удаляет существующие записи.
- Gemini-переводы — подготовить отсутствующие KK-переводы FAQ небольшими batch-запросами или перевод RU → KK для черновика страницы. В Gemini отправляется только выбранный текст без RAG-контекста. Результат сначала редактируется в preview и сохраняется только после подтверждения администратора; автоматической публикации нет.
- Администраторы — доступно только SUPER_ADMIN.
- Рассылка — создать текст, добавить фото, проверить preview и подтвердить запуск; история показывает результат.

Изменение создаёт новую ревизию черновика. До публикации пользователи продолжают видеть прежнюю опубликованную ревизию.

PAGE-кнопка может вести на любую активную страницу, включая ещё не опубликованный черновик. Пользователь увидит её содержимое только после публикации целевой страницы. Перед удалением CMS ищет все PAGE-кнопки с её key и требует сначала устранить эти зависимости. Страница `main` защищена от удаления.

## Миграции

После изменения моделей:

```bash
docker compose run --rm bot alembic revision --autogenerate -m "describe change"
docker compose run --rm bot alembic upgrade head
```

Проверяйте сгенерированную миграцию до применения и храните её в Git.

## Структура

```text
app/
  bot.py                 точка входа и composition root
  config.py              pydantic-settings
  handlers/user/         пользовательские handlers
  handlers/admin/        административные handlers
  database/models/       SQLAlchemy-модели и enum
  database/repositories/ запросы к данным
  services/              бизнес-логика и permissions
  keyboards/             inline-клавиатуры
  middlewares/           сессия БД на update
  states/                FSM
alembic/                  миграции
```

Handler-слой не создаёт engine и не выполняет сложный SQL. Бизнес-операции публикации и permissions находятся в services, поэтому их можно позже переиспользовать из REST API.

## Администраторы

`SUPER_ADMIN` управляет всем; `ADMIN` — контентом, FAQ, рассылками и статистикой; `EDITOR` — контентом и FAQ. Telegram ID — основной идентификатор. Права повторно проверяются на каждом callback, FSM-шаге и перед финальной записью. Последнего активного супер-администратора нельзя отключить, понизить или удалить. ID из `SUPER_ADMIN_ID` дополнительно защищён и всегда имеет полный доступ.

Рассылки отправляются последовательно с небольшой задержкой и повтором после `RetryAfter`; один сбой не останавливает очередь. Атомарный переход `DRAFT → RUNNING` под блокировкой строки защищает от повторного запуска одного объекта. Для нескольких инстансов или крупных баз очередь рекомендуется вынести в отдельный worker.

## Production

Логи одновременно выводятся в console и сохраняются в UTF-8 файлы `logs/bot.log` (уровень `LOG_LEVEL` и выше) и `logs/error.log` (`ERROR+`). Используется стандартная ротация; значения по умолчанию — 20 MB и 10 backup-файлов. В Docker файлы создаются в `/app/logs`; для сохранения логов при пересоздании контейнера этот путь следует подключить к каталогу или volume с правами записи для пользователя контейнера.

```env
LOG_LEVEL=INFO
LOG_DIR=logs
LOG_MAX_BYTES=20971520
LOG_BACKUP_COUNT=10
```

При обычном запуске `python -m app.bot` относительный `LOG_DIR` создаётся от текущего рабочего каталога. В логи не записываются токены бота, Gemini API key, пароль БД, вопросы, ответы, prompt или knowledge context.

Ограничьте права файловой системы на каталог `logs/` пользователем процесса бота. PostgreSQL должен быть доступен только через внутреннюю сеть Docker или localhost/firewall, с отдельным DB-пользователем и сильным уникальным паролем. Не публикуйте `5432` в Internet. Adminer в production рекомендуется не запускать; если он необходим, оставляйте localhost bind и используйте VPN/SSH tunnel либо reverse proxy с аутентификацией и IP allowlist.

- используйте длинный уникальный пароль PostgreSQL и менеджер секретов;
- не публикуйте порт PostgreSQL или Adminer;
- ограничьте ресурсы контейнеров и настройте централизованные логи/мониторинг;
- настройте регулярный backup и тест восстановления;
- для нескольких реплик замените in-memory FSM storage на Redis;
- запускайте миграции отдельным release-job до запуска новой версии.

## Stored data / Privacy

Бот хранит числовой Telegram user ID, имя профиля, выбранный язык и технические временные метки. Для статистики сохраняются просмотры страниц. Административные изменения записываются в AuditLog, а рассылки — вместе с их текстом, статусом и результатами доставки. AIUsage содержит только технические метаданные вызова: тип запроса, язык, provider/model, число найденных источников, токены, оценочную стоимость, длительность и статус ошибки. Полный вопрос пользователя, ответ Gemini, prompt и RAG-контекст в AIUsage не сохраняются.

Пример backup:

```bash
docker compose exec -T postgres pg_dump -U telegram_bot -Fc telegram_bot > telegram_bot.dump
```

Восстановление выполняйте сначала в отдельной тестовой БД и проверяйте результат перед production.
